# Plan Convergence Runbook

Operator mechanics for running `plan-convergence-run` on any plan. The methodology lives in `SKILL.md` beside this runbook.

Terms. The state directory is `~/.claude/plans/<project>/<plan-name>/`, where `<project>` names the project and `<plan-name>` is the plan's filename with `.md` removed. The coverage ledger is its `ledger.md`. The status page is its `STATUS.md`. A launch supplies the run's `args`: `planPath`, `startRound`, `stateDir`, `repoRoot`, `boardPath`, and `leadSessionId`. A by-name launch supplies `args` only through the harness's parse of the invocation, never as exact literals. A launch that must carry exact paths and a session id therefore goes through the Workflow tool, with the script body supplied directly.

## 1. Launch checks

Run every check at every launch.

1. **The subagent-model override.** Read the `env` block of `~/.claude/settings.json`. Confirm that it carries no `CLAUDE_CODE_SUBAGENT_MODEL`, unless the run deliberately pins one model. The variable overrides both session inheritance and every model the script requests per stage.
2. **The fork rule and `leadSessionId`.** Confirm that the user's settings carry a Bash allow rule for the fork command shape, `claude -p --resume`. The fork adjudicator spawns the lead-session fork through that command. Set `leadSessionId` to the launching session's id when the rule is present. Set it to the empty string when it is not; the run then takes the design-call exit to the lead instead of forking.
3. **The session-scoped freshness re-read.** The freshness pass excludes the plan's State-section facts that only the launching session can open; no subagent can open them on any agent type. Re-read each of them at launch. Mark their inventory rows discharged in the section of the round the run starts at, and record beside each mark the value read. The freshness pass reads those rows as discharged, and re-verifies any later row for one of those facts against the recorded value. Without this write, no actor ever verifies a session-scoped row, and the converged exit is unreachable. When a re-read falsifies one of those facts, record the falsification as a lead-recorded correction in that same section, on the coverage ledger's lead-edit terms (`SKILL.md`, Coverage ledger); the round's apply chain then applies and verifies it, and its verify-new seat owns the site.
4. **The ways a run stops mid-flight.** A run can stop mid-flight and return nothing in these ways: a pause on an agent permission prompt; a session limit reached mid-run; the run reaching the per-run agent budget; a throw from the script body itself, the throwing globals (`Date.now()`, `Math.random()`, argless `new Date()`) among its causes; and the lead's own stop on a mid-round correction. Record every such stop on the board as a runtime failure. Then recover it per part 2.
5. **The round-zero write.** Before a plan's first launch, write the first round's section into the ledger, under the heading `## Round <n> target set`: the round's verify-new site list and its claim-inventory table. A run that starts with no inventory rows would meet the every-row-verified condition vacuously, so this write always precedes the first launch.

## 2. Crash recovery

Ledger sections older than the two most recent recorded rounds live in `ledger-archive.md` in the state directory, located via `ledger-archive-index.md`: read the index for the section's heading and start line, then read that one section with an offset read.

Per-round, per-worker usage rows land in usage-metrics.md in the plan's state directory, appended by the round-close usage auditor; a round with no rows means that round's auditor failed, which never blocks the round.

### Exit kinds and precedence

Every exit and halt ends the run by returning its kind, the round it ended on, the state directory, and, where that round's synthesizer returned, the synthesis path. The kinds, highest first: runtime failure, reserved decision, design call, plateau, converged. One round can satisfy more than one kind, and ends on exactly one, the highest. A mid-flight stop returns nothing; the lead's recovery supplies its kind for the board record. On the null-ledger-writer path and on a mid-flight stop, runtime failure heads the order with no stage to render it.

On every halt the lead recovers, the lead writes the STATUS.md current-state line, whether or not the recovery writes the ledger, so a halt no ledger-writer recorded still reaches the page.

### Acting on a recorded kind

When a recovery resolves a kind, act on it as the run's own transitions state:

- **converged**: no relaunch; the end gate follows (`SKILL.md`, Approval bar).
- **plateau**: the lead records the structural fix in the next round's section (`SKILL.md`, The plateau response) and relaunches at that round.
- **reserved decision**: the same round, after the human decides and the lead records the decision in that round's section.
- **design call**: the same round, after the lead adjudicates and records the adjudication in that round's section; that round's synthesizer carries the recorded blocks into application.
- **runtime failure recorded by a round's own ledger-writer**: the same round when the record names the synthesizer or pre-verify as the failing stage, that round keeping the target set it already carries; the round after when it names the applier, post-verify, or a failed-seat halt, whose next-round section that ledger-writer already opened.
- **round continues**: relaunch at the round after the last recorded one.

### The journal read contract

A dead run's record is its `journal.jsonl`, under the launching session's directory in `~/.claude/projects/`: `<project-slug>/<session-id>/subagents/workflows/<run-id>/journal.jsonl`. The journal is append-ordered, each line a `started` or `result` entry, with no stage or round attribution. The lead reads it by schema shape and append position:

- Select among the `result` lines alone. `started` lines carry no return value and so no shape.
- Each stage's `schema` gives its return a distinct shape, and an entry is recognized by that shape.
- Every completed round ends at its ledger-writer. The entries after the file's last ledger-writer-shaped entry are the halted round's own. When the file carries no ledger-writer-shaped entry, every entry is the halted round's own.
- Within the halted round's entries, the entries after its synthesizer-shaped entry belong to its post-synthesis stages. A round with no synthesizer-shaped entry reached none of them.
- A batched stage's several agents leave several entries, which merge in append order into that stage's return.
- The replacement reviewer's passes each leave an entry of that stage's shape. The last one ended its cycle when its rejection set is empty, or names the same entries as an earlier pass of the same round; those rejections are the withheld entries. A last entry whose rejections are neither marks that reviewer's `null`. No entry of that shape at all, in a round whose marked entries were neither empty nor wholly excluded from review, marks that reviewer's `null` too. In a round whose marked entries were empty, or wholly excluded because every one carried adjudicated or lead-recorded text, that reviewer was never dispatched: it counts as returned, with nothing withheld.
- Any other shape with no entry marks a stage that never returned.

What the lead reads from the journal, on every recovery branch below whose round started, where the halted round reached the stages that produce them: post-verify's applied-site and failed-anchor lists; the applier's applied-anchor and failed-anchor lists; pre-verify's failed anchors; the replacement reviewer's per-entry outcomes and withheld entries; and the synthesis path the synthesizer returned, which every synthesis read below resolves against. A value no stage of the halted round produced is absent, never read.

**The adjudication duty.** On every branch whose round produced a synthesis carrying a design call, the lead first recovers from the journal every ruling and block the fork adjudicator returned, and records them in the section its recovery opens or relaunches at, since no record of them reached the ledger. Every call the fork left unadjudicated goes to its adjudicator, the lead for a design call and the human for a reserved decision, and the adjudication or the decision is recorded in that same section, on the coverage ledger's lead-edit terms.

### Recovery-set compositions

The tables below lean on the ledger-writer's two next-round compositions:

- **The apply-chain set** (the applier or post-verify returned `null`, or the applier left no journal entry): the next round's verify-new site list holds the halted round's own whole target set, pre-verify's failed anchors, and the site of every withheld entry, together with the applier's applied sites and failed anchors when the applier returned and, when it did not, the site of every marked finding the applier was given, since a stopped applier can have written any of them. The claim-inventory table is the halted round's, carried forward, plus a row for every claim those edits added or changed.
- **The ran-through set** (the applier and post-verify both returned, or counted as returned): the next round's verify-new site list is the applied sites, post-verify's failed anchors, pre-verify's failed anchors, the site of every withheld entry, and every site of the halted round's target set that the verify-new seat's per-site verdicts do not cover. The claim-inventory table is the rows still unverified, plus a row for every claim the round's application added or changed, plus one row per class the round left open.

Each failed anchor and each withheld entry in a recovered set blocks the nitpick-only close the converged bar requires.

### The kind-recovery table

On the null-ledger-writer path and on a mid-flight stop, the lead recovers, while recovering the halt, the kinds the halted round satisfied and the values that round's ledger-writer would have recorded. This table composes no ledger section of its own: a value a row routes into a round's section reaches the ledger through the recovery the halt's own table makes; an adjudication or a reserved decision reaches the section the recovery relaunches at, whether or not that recovery opens a section; and a recovered kind reaches the board record and the STATUS.md current-state write alone, never the ledger. ### The mid-flight recovery table

A mid-flight stop has no `null` stage and leaves no ledger record for the round it stopped in. That round is the run's `startRound` when no round of the run reached its ledger-writer, and otherwise the round after the last one the run's ledger-writers recorded. The round started when the journal carries an entry the read contract assigns to it, and never started when it carries none. A round that dispatched agents and had none return before the stop falls on the never-started state; its own event relaunches it at the same round and leaves the same record the started state would have. Every branch whose round started discharges the adjudication duty above, recording the adjudication or the decision in the section of the round it relaunches at. Where the stop was the lead's own on a correction, the lead also records the correction as a lead-recorded edit (`SKILL.md`, Coverage ledger), in the halted round's own section.

### The null-ledger-writer recovery table

When the ledger-writer returns `null`, whatever earlier stage of the round also did, the run returns a runtime failure with nothing written to the ledger for that round. The synthesis and the applied edits the round produced stand. The lead opens the next round's section, relaunches at the round after the halted one, and recovers on the rows below, reading the journal per the contract above.

## 3. The seeded-defect calibration

The calibration measures the opening-barrier seats' per-shape catch rate against a known answer key, and tunes the defect-shape checklist their briefs carry.

1. Copy the plan under a `-calibration` filename, `<plan-name>-calibration.md`, into that filename's own state directory, `~/.claude/plans/<project>/<plan-name>-calibration/`. That directory never collides with the plan's own.
2. Inject into the copy defects of the seat-checklist shapes: the shapes on the defect-shape checklist the seat briefs carry.
3. Record `seeded-defects.md` beside the copy, in that same directory: one row per injected defect, carrying its site, its shape, and the corruption made. This file is the answer key every returned finding resolves against.
4. Dispatch only the round's opening-barrier stages over the copy: the freshness pass, the verify-new seat, the class-audit seats, and the builder seat. Each runs on its normal model, effort, and reads, with the calibration directory as the state directory. No ledger-writer runs, and no converged bar is evaluated. Each stage takes round 1 of that directory as its round number; the ledger file is absent there, so every stage's read of it returns empty. The round-zero write does not apply to the calibration.
5. Read the catch rate per shape from the returned findings against the answer key.
6. Record the catch rate on the board.
7. Refresh the seats' defect-shape checklist against it. The checklist lives in the convergence script's seat-prompt literal, `DEFECT_SHAPE_CHECKLIST` in `~/.claude/workflows/plan-convergence-run.js`.

The calibration writes nothing outside its own directory beyond the board record. A calibration launch that stops mid-flight is recovered by a fresh launch of the calibration, not by part 2's tables: the copy and its state directory stand as the stopped launch left them, and no ledger record is owed for a launch that runs no ledger-writer.
