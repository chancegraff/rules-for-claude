# Types and Configs Per Directory

Types and configs go PER-DIRECTORY, not per source file: one `types.ts` per directory holding every top-level type declared in that directory's business-logic files, one `config.ts` (or `constants.ts` per the file's flavor) holding every top-level constant, and sub-directories getting their own. The granularity is the directory. Per-source-file sibling pairs (`foo.ts` + `foo-types.ts` + `foo-config.ts`) are banned: they optimize one architectural property (decoupled contract per file) at the cost of duplication and drift. Agents reliably fail to discover existing declarations: they don't search before writing new ones; when they do search, they search badly (wrong terms, wrong locations, verbose patterns that miss the file); and even on a hit they rationalize a new declaration ("mine is slightly different"). More small files means more hiding spots; one file per directory shrinks the search surface to "scan this one file", feasible for humans and agents. For NEW files, types/constants go in the directory's existing collection file (create one if none exists); existing per-source-file siblings consolidate in a future cleanup pass. Agent briefs introducing new types/constants must instruct an LSP workspace-symbol search for the proposed name BEFORE declaring; on a match, import from the existing location. The many-small-files cost is structural, not aesthetic; don't argue it's free. Unacceptable substitutes: "periodic dedupe passes", and lint-rule enforcement of duplicate types (ASTs can compare names but not equivalent shapes reliably).
