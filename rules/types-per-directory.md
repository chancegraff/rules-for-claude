# No Type/Config Sibling Files

Per-source-file type/config sibling pairs (`foo.ts` + `foo-types.ts` + `foo-config.ts`) are banned: they optimize one architectural property (decoupled contract per file) at the cost of duplication and drift, and more small files means more hiding spots for duplicate declarations. The many-small-files cost is structural, not aesthetic; don't argue it's free. Declaring a type or constant in the file that uses it is always fine. A directory-level collection file (`types.ts`, `config.ts`/`constants.ts`) is one acceptable home, never a mandate: do not create one just because a new file declares a type or constant, and never create one preemptively or empty. Agents reliably fail to discover existing declarations: they don't search before writing new ones; when they do search, they search badly (wrong terms, wrong locations, verbose patterns that miss the file); and even on a hit they rationalize a new declaration ("mine is slightly different"). Agent briefs introducing new types/constants must instruct an LSP workspace-symbol search for the proposed name BEFORE declaring; on a match, import from the existing location. Existing per-source-file siblings consolidate in a future cleanup pass. Unacceptable substitutes for the sibling ban: "periodic dedupe passes", and lint-rule enforcement of duplicate types (ASTs can compare names but not equivalent shapes reliably).
