# PR Splits

- Splitting a PR: never rewrite, force-push, or append to the original branch; it is the user's reference and rollback point, and review history lives there. Create new branches from main, `git cherry-pick` the existing commits in, and fix up the NEW branches. Preserve original commit messages verbatim, even messy squash bodies (the user's squash message is theirs). The old PR gets a link comment and is closed. Re-authored "equivalent" code in a split forces re-review of code that was already reviewed.
- Every stacked layer must be functionally sound on its own: no hook that slices with no controls wired to it, no query-less wrapper, no half-carried feature. Intermediate layers MAY therefore differ in content from the final tree; the invariant that survives is that the top of the stack recomposes byte-identically to the reviewed end state (`git diff <orig>` empty is the gate). Never re-author "cleaner" versions during a split. A reviewer finding that a layer is broken in isolation is valid; don't deflect it as "intentional stacked state". A rename carries its stories and tests through (renamed too, with imports, titles, and describe blocks updated), never deleted.
- Split mechanics that work: `git cherry-pick -n <commit>` on the new base branch stages everything for one clean commit, with deletions applied on top; the stacked branch is `git cherry-pick <commit>` with conflicts resolved to the incoming version verbatim. `git restore --source=REF -- path`, `git show REF:path > file`, and `git checkout-index` are deny-listed for teammates; stage exact blobs via `git update-index --cacheinfo` plus Write, gated by per-file `git diff REF` empty.
- A branch the user has reviewed gets fix commits on top, never a rewrite (preserves review anchors); unreviewed upper layers may be rebuilt and force-pushed. Amend and reset are off-limits regardless; squash-merge collapses fix commits.
