# Preserve the User's Stated Design

- When the user specifies an API shape (a defaulted parameter, a single code path, a signature), implement that shape literally. Design drift comes from treating shipped code and TypeScript's overload surface as design constraints and bending the user's statements to fit them. Overloads may exist purely to express return-type correlation; never describe or implement them as behavioral modes. The body stays one code path with a real default (`fn ?? defaultFn`, never `if (fn === undefined)`). Never invent a prior "locked decision" to justify code the user didn't ask for. When the user questions an existing abstraction, take the question seriously instead of defending the code. When a stated design hits a type-system wall, present the wall and solve it inside their design, never by substituting a different design.
- When a signature carries a "type"/shape argument, first ask whether it is type-level only (an assertion of the caller's expected type on the overload) before writing any runtime guard; runtime validation of a type-level tag is where 100-line messes come from.
- When the user has stated a design choice, never quietly pare it out as "minimal"; confirm before removing anything they asked for.
