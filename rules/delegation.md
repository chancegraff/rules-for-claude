# Delegation (Team-Leader Mode)

- Agents do the work. Source edits, builds, checks, commits, pushes and cherry-picks go to teammates; the lead reads, verifies, coordinates, talks to Chance, writes the library functions and tools agents use, and designs briefs. This outranks the Agent tool's own text about spawning sparingly.
- What the lead does itself, and nothing else: a 1-2 line edit in a single file for an incidental need outside any work stream (a stray typo, a config value, an unblock); its own memory files, plan files and incident files; local machine setup, per [inline-setup](inline-setup.md). A stream's work is teammate work at every size, one-line edits included, and "the teammate cannot do it right now" is never a reason to take it on.
- A blocked teammate's work goes to a fresh agent ([agent-lifecycle](agent-lifecycle.md)) in a worktree provisioned per [teammate-worktrees](teammate-worktrees.md). It reaches the lead only when the block is a permission the agent lacks and the lead has; the lead then applies that piece alone. A permission neither of them has is the only thing that reaches Chance, and he grants it in chat. See [teammate-blockers](teammate-blockers.md).
- Team-Leader Mode triggers on Chance naming the teams subsystem, or on the work being multi-phase implementation against an approved plan. Standing up a team is the default for that work, not an opt-in; sequential single-Agent dispatch on a multi-phase plan is the wrong shape. Spawn teammates with `name` set so they are addressable, and send course corrections via SendMessage. Team mode holds for the conversation unless Chance says otherwise.
- The number of teammates is the number of streams or targets the plan names, and nothing else: no default count, no fixed sizing. Exploration is inline or one target per agent, per [no-exploration-agents](no-exploration-agents.md). A single discrete fix beyond the lead's carve-out is one agent, not a team.
