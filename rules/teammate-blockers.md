# Teammate Blockers Escalate to the User

A teammate blocker (a worktree it can't reach, missing dependencies, a pending permission prompt, a denied tool shape) is an escalation to the user, never a reassignment to the lead. Absorbing the blocked stream into the lead's own session is the failure mode: it bypasses [delegation](delegation.md), kills cross-review (the lead cannot independently review work it authored), and converts a provisioning problem into unreviewed lead-authored work. The lead's 1-2 line carve-out never stretches to cover a blocked teammate's stream, no matter how close to done the stream looks or how much context the lead holds. "I'll do the git for this stream myself" is never one of the options.

The sequence: stop that stream, report the blocker to the user with the exact unblock (name the teammate, the failure, and where applicable a ready-to-run `! <command>` line), and wait. After the user unblocks, resume the teammate via SendMessage, or respawn a fresh one per [agent-lifecycle](agent-lifecycle.md) into a properly provisioned worktree ([teammate-worktrees](teammate-worktrees.md)). Rejecting a teammate's workaround that routes around a deny rule (e.g. pinned `--git-dir`/`--work-tree` to dodge a denied `git -C`) is correct, but the follow-up is escalation, not the lead running the commands itself; deny rules bind lead and teammates equally ([shell-composition](shell-composition.md)). If the user calls out lead-authored work mid-incident, halt immediately, including any in-flight edit; recovery is escalation and respawn, never finishing the piece first. Companion: [tool-unavailable](tool-unavailable.md) is the same principle for the lead's own missing tools.
